Overview

Dreamer Studio is a local Windows desktop studio for one user to manage a creative library (novels first, music and video later) and run AI analysis on it. It ships as a portable package: an Electron app that starts a bundled Python FastAPI backend on 127.0.0.1. All data stays on the machine.

Tech stack

  • Shell: Electron main + preload + renderer (AD-01)
  • UI: Angular + Bootstrap reboot and utilities only (AD-26) + SCSS, Storybook 10 (AD-07, AD-28); fonts from npm (AD-27); i18n with own JSON files, no library (AD-07)
  • Backend: Python FastAPI, pip + venv (AD-02, AD-09)
  • Storage: SQLite via node:sqlite in main for operations and history (pipeline runs, logs); library data (metadata, chapters, covers) as files in app data, one metadata.json per novel (AD-03, AD-04, AD-38)
  • Packages: Dreamer package = .zip read with yauzl, written with yazl (TH03-01 Q-01); format in _docs/2.dreamer-package-format.html (TSK-012)
  • Tooling: pnpm workspaces; ESLint, Prettier, Vitest; Ruff, pytest (AD-09); esbuild for main + preload (AD-19)
  • Logging: electron-log in main (renderer via IPC), stdlib logging in Python; daily files, kept 7 days (AD-12, AD-20)
  • Build: PyInstaller one-folder + electron-builder zip, Windows x64 only (AD-10, AD-11, AD-21)

Quality attributes

  • Portable: runs after extract, no extra installs (TSK-004)
  • Responsive UI: long work runs as pipelines (TSK-008)
  • Data safety: one backup before migrations (no rollback, AD-25), atomic import (TSK-006, REQ-013)
  • Observable: file logs, diagnostics, error handler (TSK-003, TSK-011)
  • Localized and themed at runtime (REQ-002, REQ-007)

Key decisions

  • AD-04 DB owned by main; Python is stateless
  • AD-05 Pipeline executor in main; Python runs heavy steps
  • AD-06 Renderer → main via typed IPC only; main → Python over HTTP
  • AD-12 One log file per process, same format
  • AD-13, AD-18 settings.json fixed in %LOCALAPPDATA%/DreamerStudio; app data folder switchable live (REQ-008, AD-37)
  • AD-22 Raw SQL + thin typed Database wrapper; features use repositories only
  • AD-30..AD-32 Pipeline runs: live log pushed, UUID run IDs, history in keyset pages of 50
  • AD-33, AD-34 Backend jobs: one streaming NDJSON request per job, cancel = abort the request; the demo's step 3 runs in Python
  • AD-35 IPC invoke results are { value } | { error: AppError }; the preload rejects with the AppError
  • node:sqlite works in Electron 44.9.0 (SQLite 3.53.4), dev and package (AD-03, TSK-005)

Storage and startup

TSK-005, TSK-006, TSK-007. Electron main owns the database (AD-03, AD-04, AD-22..AD-25).

  • Startup order in main/index.ts: settings.json load (module load, sync) → single-instance lock → whenReady → app data root check (dialog) → AppDataManager.open(root) (folders → logger → database → migrations → pipeline recover) → error handlers → IPC → window → backend. No lock → quit; a second launch restores and focuses the first window.
  • Settings (TSK-010, AD-36): SettingsStore reads settings.json once at startup. Missing → defaults written. Invalid fields → their defaults, file rewritten. Bad JSON or not an object → copied to settings.json.bak, defaults written. Other read errors → defaults in memory, file untouched. Writes go through settings.json.tmp + rename; a write failure is logged and the value kept in memory. The notice is logged after the logger starts and reaches the renderer through settings:get (toast at startup).
  • Settings changes (REQ-006): settings:update(patch) checks the patch with validateSettingsPatch (only language, theme, pipelines; appDataDir is refused) → SETTINGS_INVALID with the field in details, nothing changed. settings:reset('general' | 'pipeline') restores that section's defaults. Each change is kept in memory, written, then pushed as settings:changed; a write failure still keeps and pushes the value, then returns SETTINGS_WRITE_FAILED.
  • Dreamer package (TSK-012): readPackage(path) in main checks a .zip without writing anything: size and entry limits from the central directory, then counted bytes while inflating; unsafe or duplicate names refused; metadata.json (version 1, type novel, fields, BCP-47 language); chapters strict UTF-8, normalized with shared/core/novel-text.ts, SHA-256 of the normalized text; cover by magic bytes. Result: refusal (notZip, unsafePath, unsupportedType, tooLarge, problems with every problem) or a preview with warnings (empty chapter, same text, ignored files). Codes, not text: the import screen (REQ-013) translates them. Unexpected read errors are logged (module library) and shown as notZip. Spec: _docs/2.dreamer-package-format.html.
  • Library storage (TSK-013, AD-38): each novel is library/<uuid>/ with metadata.json (v1: metadata, tags, publication, dates, ordered chapters { title, file, paragraphs, chars }), optional cover.jpg|png and chapters/<sha256>.txt (normalized text; same text = one file). Names come only from UUIDs and hashes. Writes go through one atomic helper (.tmp → fsync → rename); chapter files and cover first, metadata.json last (saveMetadata then removes unreferenced files). withNovelLock(id) serializes writes per novel. Delete = rename to cache/trash, then remove. AppDataSession.open runs cleanLibrary after migrations: removes cache/import/*, cache/trash, *.tmp and unreferenced chapters of valid novels; folders with invalid metadata are kept for the self-check library.files (category storage). No library data in SQLite.
  • Novel import (REQ-013): library:read-package returns the preview (nothing written); library:import(request) starts pipeline novel-import through executor.startRun(type, params, label, novelId = null) (label = edited title; import gets its novel id only on success). Steps: check (size and mtime unchanged, else PACKAGE_CHANGED; package read again), extract (ticked chapters → writeChapter into cache/import/<run-id>, empty title → "Chapter n", cover from the package / a picked file / none, progress per chapter, checkpoint after each), save (metadata.json in staging, then one rename to library/<new uuid> = the commit, retried on EPERM / EBUSY / EACCES; ctx.setNovelId). Write errors → LIBRARY_WRITE_FAILED. cleanup removes staging on cancel and on failure (executor runs cleanup for both); app close / crash leftovers are removed by cleanLibrary at the next start. pipeline_run has label and novel_id (migration 0.1.0_1), used by the toast "Open novel" (/library/:id, Coming soon until REQ-023) and later by the Library list (REQ-014).
  • Library screen (REQ-014): LibraryIndex is built by AppDataSession.open (sync scan of library/*/metadata.json; a missing or invalid file, or an id that differs from the folder, is skipped and logged), so an app data switch rebuilds it. executor.onRunFinished runs before the final pipeline:update: a succeeded novel-import refreshes that novel and broadcasts library:changed { novelIds }. library:list → NovelSummary[], library:get(id) → NovelDetail (summary + description + chapters [{ position, title, file, paragraphs, chars }]) or NOVEL_NOT_FOUND, library:open-folder(id) → shell.openPath. Covers: read-only library-file://cover/<novelId>?v=<updatedAt> (GET only, UUID in the index, path from library-files.ts, Content-Type from magic bytes, else 404); the CSP adds only img-src library-file: (TSK-025 cover part). Search, filters and sort run in the renderer on the full list.
  • Novel edit (REQ-015): library:update-novel({ id, patch }) → LibraryService.updateNovel inside withNovelLock: lock check (NOVEL_LOCKED, run label in details), merge + trim + normalizeTags, original title / title / language required (NOVEL_METADATA_INVALID), cover 'keep' | 'remove' | { path } (new file written first, COVER_INVALID), new updatedAt, saveMetadata (metadata.json is the commit point, then other covers and unreferenced chapters removed), index refresh, library:changed. Lock = a pipeline_run with this novel_id in queued or running (NovelSummary.lock); reads never check it; startup recovery ends old runs, so a restart clears it. library:pick-image checks the file and returns a data: preview. Renderer: inspector Edit / Change cover / Remove cover disabled with the lock reason; leaving a dirty form (other novel, other page) asks "Discard changes?".
  • Novel delete (REQ-017): library:delete-novels(ids) → LibraryService.deleteNovels → { deleted, skipped }; per novel in withNovelLock: unknown id ignored, locked → skipped, else deleteNovel (folder renamed into cache/trash/, then removed; startup cleanup empties the trash) and dropped from the index; one library:changed for the deleted ids (also sent before a LIBRARY_WRITE_FAILED stops the batch). Renderer: one NovelDeleteDialog on the library page, opened from the inspector Delete (disabled while editing or locked), the selection bar and the list row; it names the novel or the count, lists busy novels as skipped, or shows "Nothing to delete".
  • Novel export (REQ-018): library:export(id) → native Save dialog (default safeFileName(title).zip, last export folder kept in memory; cancel → null) → startRun('novel-export', { novelId, outputPath }, title, novelId), so the novel is locked from insert (queued) until the run ends; export itself is allowed on a locked novel. Steps: snapshot (metadata.json, cover and every chapter file exist, else NOVEL_NOT_FOUND / CHAPTER_FILE_MISSING), write (writePackage: package metadata.json incl. publication, cover, chapters as chapters/0001.txt… in order with a blank line between paragraphs, into <target>.tmp), finish (rename over the target, retried). Write errors → LIBRARY_WRITE_FAILED; cleanup deletes the .tmp on fail / cancel; PipelineDefinition.discard(params) deletes it for runs ended by startup recovery or cancelAll. library:show-export(runId) → shell.showItemInFolder for a succeeded export (path from run params). Renderer: inspector Export → toast "Exporting…" + View in Pipelines; PipelineStore toasts "Exported" + Show in folder, or "Couldn't export" + View log.
  • Chapter text (TSK-025): library:get-chapter({ novelId, file }) → { paragraphs }; file must be a content hash listed in the novel's chapters (index), path built by chapterPath; else CHAPTER_FILE_MISSING; never checks the lock. Consumer: NovelStore of the novel page (REQ-019); a missing file shows the reader error state with Try again.
  • Self-checks (TSK-011): SelfCheckEngine in main/index.ts; features add checks with engine.register(check) (duplicate id → error at startup). diagnostics:run runs all checks in parallel, 5 s timeout each; a throw or timeout → error diagnostics.check.failed / .timeout, the others still run; a second call joins the running one. CheckContext is built per run from manager.session() (paths, checkDatabase(), settings load result, backend state, /health ping with 3 s timeout), so a run during a switch fails with APP_DATA_SWITCHING. Built-ins: storage.appData, storage.settingsDir (probe), storage.diskSpace (warning < 1 GB or unknown, error < 100 MB), database.integrity, backend.reachable (starting = warning), settings.file (invalid fields = warning, unreadable = error). Results carry i18n keys + params (shared/models/diagnostics.ts), the renderer translates; counts logged once (module diagnostics); nothing stored.
  • App data root (TSK-010 AC-4): app/dialogs/app-data-dialog.ts runs before anything else starts. The default root is always created; a custom root that is missing or not writable (probeWritable) → native dialog: Choose another folder… (picker, checked again) · Use default folder (hidden when the default fails) · Quit. The chosen folder is saved as appDataDir.
  • Folders: ensureFolders(paths) creates library, logs, cache on every start, before the logger (TSK-007 AC-2, AC-3). Failure → APP_DATA_UNWRITABLE dialog (Quit only), then quit; nothing else starts.
  • Paths: resolveAppPaths(root) → AppPaths, built by AppDataSession.open(root). Error handlers, IPC and the backend read them through getters on the one AppDataManager (paths(), session()), so they follow a live switch (AD-37). No other code joins app data paths.
  • App data switch (REQ-008): app-data:pick-folder (native picker) → app-data:inspect(path) (write probe; history of its database.sqlite read with an immutable read-only connection vs the bundled migrations → none | current | older | newer; nothing written) → app-data:switch(path). The switch refuses while pipelines are queued or running (APP_DATA_PIPELINES_ACTIVE) or a folder that is missing / not writable (APP_DATA_UNWRITABLE), then: stop backend → close the old session (WAL checkpoint) → open the new one → save appDataDir → restart backend; each step pushed as app-data:progress, then app-data:changed (AppInfo) and settings:changed. While switching, session() throws APP_DATA_SWITCHING (e.g. pipeline:start). Failure → rollback step, the old folder is reopened and the original code returned; if the reopen fails → fatal data dialog. The previous folder is never changed or deleted. Outcome logged (module app-data).
  • storage/database.ts: Database.open(file) sets busy_timeout = 5000, journal_mode = WAL, synchronous = NORMAL, foreign_keys = ON; get / all / run / exec / transaction; statements cached per SQL; close() checkpoints the WAL.
  • Query error: logged (module storage, SQL text, no parameters), kept as last error, thrown as DB_QUERY_FAILED.
  • checkDatabase(db): SELECT 1 + PRAGMA quick_check + last error → CheckOutcome (ok / warning / error with i18n keys), for the self-checks (TSK-011).
  • storage/migrator.ts: loadMigrations(dir) reads *.sql from migrationsDir() (dev electron/main/storage/migrations/, packaged <resources>/migrations/), checks names and sorts them; runMigrations(db, migrations, backupFile) runs the pending ones.
  • Schema version: table sys_migration_history(id, version, upgrade_num, applied_at), one row per applied file, created by the first migration 0.0.0_0__sys_migration_history_table.sql (AD-23).
  • Run: applied id unknown to the app → DB_NEWER_VERSION, no writes; rows exist and files pending → VACUUM INTO database.backup.sqlite (AD-25); each file exec, then its row. A failure stops the run with no rollback → DB_MIGRATION_FAILED.
  • Dev only: DREAMER_DEV_FAIL_MIGRATION=1 adds a failing migration 999.0.0_0__dev_fail; DREAMER_DEMO_TICK_MS sets the demo pipeline tick (TSK-009).
  • Repositories: storage/repositories/<table>-repository.ts, take a Database, return shared/models types. First one: PipelineRunRepository (TSK-008).
  • Table pipeline_run (0.0.0_1__pipeline_run_table.sql): UUID id (AD-31), type, status (CHECK queued / running / succeeded / failed / cancelled), cancel_reason (user / appClosed), params JSON, progress, step_index / step_count / step_name (i18n key), error_code, error, ISO UTC times; no display text and no log path stored.

Pipeline executor

TSK-008, AD-05, REQ-009. electron/main/features/pipelines/; created in main/index.ts after migrations.

  • PipelineExecutor(repo, paths, registry, limit): in-memory queue; starts the oldest queued run while running < limit() (settings.pipelines.maxConcurrent, 1–5, default 1; REQ-009). Every settings change calls limitChanged(), which starts queued runs at once; lowering the limit never stops running runs. The only writer of run status: queued → running | cancelled; running → succeeded | failed | cancelled.
  • A pipeline = PipelineDefinition with ordered async PipelineSteps and optional cleanup. Steps get a StepContext (params, signal, progress, log, checkpoint) and must use sleep(ms, signal) or checkpoint() so Cancel can stop them.
  • Progress: overall % from step index + step %; DB write and pipeline:update at most every 250 ms per run, at once on step or status change.
  • Cancel: queued → cancelled at once, no log file; running → AbortController.abort(), the step rejects at its next checkpoint, cleanup runs, then cancelled (reason user). A throwing step → failed with error_code (CodedError code) and message; stack in the run log and main log.
  • Run log: <app data>/logs/pipelines/<id>.log, AD-12 line format (module pipeline.<type>), new lines pushed as pipeline:log every 250 ms (AD-30); kept until the run is deleted (main log cleanup only matches main-*.log).
  • Recover at startup and cancelAll on quit: one UPDATE of queued / running rows → cancelled, reason appClosed (returns id, type, params), then the definition's optional sync discard(params) per run (export: delete .zip.tmp), plus a sync "Cancelled: app closed" log line.
  • Registry: PipelineRegistry(definitions); dev holds the demo pipeline, the package holds none, so pipeline:types returns [] there and the Start button is hidden (TSK-009 AC-3).
  • Demo pipeline (demo-pipeline.ts, TSK-009): 5 steps × 10 ticks of DREAMER_DEMO_TICK_MS (default 300); step 3 runs as the backend job demo; failAtStep = n fails at the 5th tick of step n.
  • IPC (PipelineChannel, DreamerApi.pipeline): invoke pipeline:types | start | cancel | list | get | get-log | delete; push pipeline:update (whole run), pipeline:deleted (ids), pipeline:log. list = newest first, filters (finished, statuses, types), keyset cursor + total (AD-32). Errors PIPELINE_NOT_FOUND, PIPELINE_UNKNOWN_TYPE.

Backend jobs

TSK-009, AD-33, AD-34. Main backend/backend-job.ts, Python backend/app/jobs/.

  • POST /jobs/{type} with the token, body = params JSON; response application/x-ndjson, one event per line: progress (percent), log (level, message), done, error (JOB_FAILED, message). Unknown type → 404 JOB_UNKNOWN; body not an object → 422 JOB_PARAMS_INVALID. No state kept (AD-04).
  • runBackendJob(type, params, ctx) maps events to ctx.progress / ctx.log (prefix [backend.job]); an error event fails the step with its message; no connection (getBackendConnection() is null unless the backend is running), non-2xx or a stream without done → BACKEND_UNAVAILABLE.
  • Cancel: ctx.signal aborts the fetch; Python stops on disconnect and logs "job cancelled" (verified through the token middleware).

Build and Release

TSK-004. Portable Windows package, no installer (AD-10, AD-11, AD-21).

  1. Prerequisites: Windows x64 dev machine, pnpm install, pnpm py:setup.
  2. Set the version in the root package.json (single source, TSK-002 AC-4).
  3. Run pnpm package (about 3 minutes). It runs, in order, and stops on the first failure:
    1. ng build → angular/dist/browser/
    2. esbuild → electron/dist/ (main + preload, with APP_VERSION and today's UTC BUILD_DATE)
    3. node scripts/py.mjs freeze → PyInstaller → backend/dist/dreamer-backend/
    4. electron-builder → dist/DreamerStudio-<version>-win-x64.zip (about 165 MB)
  4. Release check: extract the zip on a clean Windows 10/11 x64 machine (or Windows Sandbox), run DreamerStudio.exe, and confirm the window, the version and no backend banner. Logs are in %LOCALAPPDATA%/DreamerStudio/logs.
  5. Linux (ad hoc): run the same steps on an Ubuntu x64 machine (PyInstaller does not cross-compile) → dist/DreamerStudio-<version>-linux-<arch>.AppImage. Data and logs are in ~/.config/DreamerStudio. Ubuntu 22.04+ needs libfuse2 to run an AppImage.
DreamerStudio-<version>-win-x64/
├── DreamerStudio.exe           # Electron app
└── resources/
    ├── app.asar                # electron/dist + package.json; no node_modules (all bundled by esbuild)
    ├── renderer/               # Angular build, served from app://
    └── backend/                # dreamer-backend.exe + _internal/ (Python, libs, VC++ runtime DLLs)
  • Nothing to install on the target: Python, the libraries and the VC++ runtime ship inside resources/backend.
  • The backend is a console exe started with a hidden window, so its stderr goes to the main log.
  • dev:crash is not registered in the package.
  • No code signing and no auto-updater yet. Antivirus may flag the PyInstaller exe; one-folder and no UPX lower the risk.
  • App icon is the Electron default; the brand mark is in angular/public/logo.svg (REQ-001) but not wired into the package yet.

Conventions

Code style is set by the human. TSK-001 is approved, so all groups below are final; the TSK-002 code follows them.

Code style
  • No comments on classes, functions, properties or methods.
  • Keep other comments short; never explain code at length.
  • Keep code simple and readable.
  • One import statement per line; never wrap an import over several lines.
  • Do not break a line that is not too long.
  • No duplicated code; refactor into a function or class.
  • TypeScript: no Omit type; always write explicit types.
  • Write unit tests only when the human asks for them explicitly.
  • Use the data-testid attribute to target elements in tests.
  • Angular: each component has its own <name>.component.html (templateUrl) and <name>.component.ts; no inline template.
  • Angular: no component stylesheet (styles, styleUrl); add styles as global SCSS partials in angular/src/styles/components/_<name>.scss, scoped under the component selector and loaded from styles.scss.
  • Angular: import through the aliases @components/*, @core/* and @shell/* (angular/src/<folder>/*), set in angular/tsconfig.json; relative paths only inside the same folder.
  • Electron: import electron/main/storage/* through the alias @storage/*, set in electron/tsconfig.json (esbuild) and vitest.config.ts.
  • Angular: every boolean input uses { transform: booleanAttribute }, so a bare attribute (<ds-card interactive>) works.
  • Storybook: stories in angular/stories/<group>/<name>.stories.ts, not next to the code; inline templates are allowed in stories only.
  • Angular: do not split a component only to show another state or variant; use inputs (e.g. variant) on the same component.
  • Angular: shell parts that sit in the .ds-app grid use attribute selectors on the landmark (header[dsTopbar], nav[dsRail], footer[dsStatusBar]); pages are <name>.page.ts with an h1 dsPageTitle.
  • Angular: modules, rail and routes come from one registry (shell/registry/modules.ts); a module with page: null opens the Coming soon page; unknown paths go to Home. A module with detailRoute also gets <id>/:id; subRoutes ({ path, page, title }) add fixed pages under the module, before :id, with the title in the breadcrumb (e.g. /library/import, REQ-013). Every module route has canDeactivate calling the page's optional canLeave() (REQ-015). detailPage replaces page on :id (Library: NovelPage, REQ-019).
  • Base href: ./ in the production build (loaded from app://), / in the development build so deep links like /pipelines/<id> reload under pnpm dev.
  • Prettier formats angular/src/**/*.html with the angular parser (.prettierrc override), so control flow blocks stay indented.
Naming and formatting
  • TS: kebab-case files, PascalCase types/classes, camelCase functions; Prettier + ESLint
  • Python: snake_case, Ruff format + lint, type hints
  • IPC channels: <domain>:<action>, e.g. pipeline:start; types live in shared/
  • UI text only from i18n keys in shared/i18n/{en,vi}.json (AD-29), read by I18nService + t pipe in the renderer and app/app-i18n.ts in main (no i18n library); missing key falls back to English, then the key
  • i18n keys: single-quoted literals (check-i18n finds them), namespaces app nav rail topbar status state home run soon module pipelines toast errors dialog common; the only built key is errors.<CODE>.*; id: '…' literals (e.g. self-check ids) are not keys and are skipped
  • Base components (components/) take text through inputs; the app passes translated text
  • UI styles only from DESIGN.md tokens
Error handling and logging
  • Errors cross process boundaries as { code, message, details }; renderer translates code into a friendly message (TSK-003 AC-4, REQ-002)
  • IPC invoke (AD-35): main registers handlers with handle(), which returns { value } or { error: AppError } (CodedError keeps its code, anything else is logged and becomes MAIN_UNEXPECTED); the preload call() rejects with the plain AppError, so the renderer can check error.code (isAppError); AppErrorHandler uses that code
  • Global handlers: main uncaughtException/unhandledRejection, renderer ErrorHandler, FastAPI exception handler
  • Log line: ISO UTC time · level · process · module · message, stack on the next lines; a new file each local day, files older than 7 days deleted; never log secrets
  • Main: createLogger(module) from electron/main/logging; renderer: DesktopApi.writeLog → log:write; Python: logging.getLogger(name)
  • Friendly errors: renderer and main rejections → error banner; main exception and renderer crash → native dialog; backend down → warning banner; startup data error → fatal data dialog, then quit (app/dialogs/fatal-dialog.ts)
Data access
  • Features read and write data only through repositories (TSK-005 AC-2, AD-22)
  • Only electron/main/storage/ may import node:sqlite; only storage/, app/app-data-*.ts and main/index.ts may import storage/database; ESLint no-restricted-imports fails the build otherwise (unit tests electron/**/*.test.ts are exempt, they open a temp DB)
  • Raw SQL with ? parameters; never build SQL from values
  • App data paths only from AppPaths; ESLint no-restricted-syntax fails on app.getPath or process.env.LOCALAPPDATA outside storage/paths.ts (TSK-007 AC-4)
  • Schema changes only as migration files <version>_<upgrade_num>__<name>.sql in electron/main/storage/migrations/: version = the app release that ships it, upgrade_num from 0 inside that release, name in snake_case (AD-24)
  • Never edit a released migration file; ship a fix as a new file
Testing
  • Tooling: Vitest (TS), pytest (Python), next to the code (AD-09)
  • Unit tests only when the human asks; elements under test carry data-testid
  • UI states: Storybook stories per component in angular/stories (REQ-001); check with pnpm storybook + tool-playwright
  • AC checks in the running app: tool-playwright
Git and commits
  • One plan step = one commit: <type>(<scope>): <summary> [<req-id>]
